# ADR-0010: 마켓 로고 — ADR-0009 §1 의 적용범위를 **식별 표지**에 한해 한정

- 상태: 승인 (2026-08-06, 사용자 판정) — ADR-0009 §1 의 **재결정**
- 관련: [ADR-0009 원문 링크·판매자 미디어](0009-source-links-and-owner-media.md)(§1 을 수정) ·
  [ADR-0003 IG 1층 fixture](0003-ig-businessdiscovery-fixture.md)(같은 App Review 벽)
- 영향: `data/slime_market_kb_demo.json`(`markets[].logo`), `data/market_logos/`(신규),
  `slime_rag/source_links.py`, `slime_rag/logos.py`(신규),
  `slime_rag/sources/apify.py`, `slime_rag/linking.py`, `slime_rag/pipeline.py`, `app/ui.py`

## 맥락

UI 에서 마켓은 `market_word` 문자열 하나로만 표시된다(사이드바 `1층 스펙 · 머머`). 슬라임
마켓은 사용자에게 **브랜드로 인지되는 대상**이라 이름만으로는 어느 마켓인지 즉시 붙지 않는다.
마켓 본인 인스타 프로필 아바타를 붙이면 그 갭이 메워진다.

데이터는 이미 값을 치르고 있다. `InstagramProfileSource` 가 돌리는
`apify/instagram-profile-scraper` 응답에 `profilePicUrl` / `profilePicUrlHD` 가 들어 있는데
(`data/apify_profile_murmur_raw.json` 스냅샷이 증거), `_to_review()` 가 `latestPosts[]` 만
훑고 프로필 레벨 필드를 버린다. 새로 긁을 것은 없다.

**그런데 ADR-0009 §1 과 정면으로 충돌한다.** §1 은 이렇게 못박았다:

> 저장하는 것은 **주소**뿐이고 … 따라서 다운로드·재호스팅은 **배제**한다 — 원칙 위반이기도
> 하지만, 실무적으로도 인스타 CDN URL 은 수일 내 서명이 만료돼 죽는다.

핵심은 이 충돌을 **우회할 수 없다**는 것이다. 인스타는 만료되지 않는 아바타 URL 을 제공하지
않는다 — `profilePicUrlHD` 는 서명 파라미터(`_nc_ohc`, `oe`)를 달고 수일 내 죽고, 살아 있는
동안에도 CDN 이 referrer 를 본다. 게시물에는 `/p/{shortcode}/embed` 라는 **안정적인 주소**가
있어서 §1 이 성립했지만, 프로필 아바타에는 그에 해당하는 것이 없다.

즉 §1 을 문자 그대로 두면 로고 기능은 **구성상 불가능**하다. 그리고 §1 이 다운로드를 반대하며
근거로 든 '만료' 사실이, 로고에 한해서는 다운로드를 **유일하게 동작하는 방법**으로 만든다.
같은 사실이 반대 방향을 가리킨다 — 그래서 우회가 아니라 재결정이 필요하다.

## 결정

### 1. §1 의 적용범위는 **리뷰 대상 저작물**이다 — 식별 표지는 아니다

ADR-0009 §1 의 "다운로드·재호스팅 배제"가 지키려던 것은 **후기 본문과 게시물 미디어**,
즉 이 서비스가 리뷰하고 인용하는 저작물이다. 그 바이트를 우리 서버에 복제하면 원저작자의
유통을 대체하게 된다 — 그게 무재배포 원칙의 실체다.

마켓 프로필 아바타는 그 범주가 아니다. 리뷰의 **대상**이 아니라 리뷰 대상을 **가리키는 표지**이고,
그 마켓을 지칭하기 위해 그 마켓의 표지를 쓰는 지명적(nominative) 사용이다. 아바타를
재호스팅해도 원저작자의 어떤 유통도 대체하지 않는다.

→ **§1 은 후기 본문·게시물 미디어에 적용된다. 마켓 본인 프로필 아바타는 예외다.**

### 2. 예외의 경계 — 넘지 않는 선을 먼저 못박는다

예외는 그 폭이 명시될 때만 예외다. 아래를 벗어나면 이 ADR 의 허가 범위 밖이다.

| 항목 | 한계 |
|---|---|
| 개수 | 마켓당 아바타 **1개**. 갤러리·히스토리 없음 |
| 해상도 | **≤320px, 로컬에서 강제**(아래 ⚠️). 원본 추적·업스케일 안 함 |
| 출처 | **그 마켓 본인 계정만**. `relatedProfiles[]` 의 타 계정 아바타는 수집하지 않는다 |
| 링크백 | 로고를 그리는 자리엔 **항상** `instagram.com/{handle}` 링크를 같이 그린다 |
| 게시물 미디어 | **여전히 전면 금지** — ADR-0009 §4 무변경. 유저 후기 미디어도 그대로 금지 |

⚠️ **해상도 경계는 URL 이 아니라 코드가 지킨다** (2026-08-06 실측). `profilePicUrlHD` 의
`stp=dst-jpg_s320x320` 는 **요청일 뿐**이고, 인스타 CDN 은 원본이 더 크면 이 힌트를 무시하고
네이티브 크기를 준다 — 첫 수집 13건 중 **9건이 518~1080px** 로 도착했다. URL 을 믿고 그대로
저장했다면 판매자의 **원본 해상도 브랜드 자산**이 커밋됐을 것이고, 아래 §'정직한 인정'의
'저해상' 완화 논거가 무너진다. 그래서 `logos.normalize()` 가 저장 시점에 320px 로 줄이고
(`Pillow`, 이 때문에 명시 의존성이 됐다), `eval/test_source_links.py` 가 **커밋된 산출물을
직접 재서** 게이트한다 — 프로세스가 아니라 결과물을 검사한다.
실측 효과: 588KB → 192KB(13개), 전량 320x320.

### 3. 폴백은 기능이 아니라 **철회 경로**다

`source_links.logo_asset()` 은 절대 None 을 돌려주지 않는다. 파일이 없거나·KB 에 `logo` 가
없거나·경로가 `data/market_logos/` 밖으로 벗어나면 **모노그램 칩**(`market_word` 첫 글자 +
이름 해시 색상)으로 degrade 한다. `embed_url()` 과 같은 fail-closed 형태다.

이건 결손 처리용 편의가 아니라 이 결정의 **리스크 완화 장치**다. 판매자가 내려달라고 하면
`data/market_logos/{handle}.jpg` **파일 하나를 지우는 것**으로 즉시 철회되고, UI 는 코드 변경
없이 모노그램으로 돌아간다. 철회 비용이 낮다는 사실이 이 예외를 감당 가능하게 만든다.

## 결과

- 마켓 선택 시 사이드바 1층 패널에 로고 + `@handle` 링크가 뜬다. 로고는 판매자 공식 자산이라
  1층(공식 스펙) 패널이 개념상 맞는 자리다.
- 저장소에 서드파티 바이트가 **처음으로** 들어온다(13파일 ~250KB). Render 파일시스템은
  휘발성이라 커밋된 것만 배포본에 남는다 — 런타임 캐시로는 데모가 성립하지 않는다.
- 수집은 1회성 수동 실행이다(`python -m slime_rag.logos`). 자동 갱신 없음 — 로고는 거의
  안 바뀌고, 자동화하면 감시 없는 반복 재호스팅이 된다.
- 표시 정책은 `source_links.py`(순수 모듈)에 있어 무비용 CI 가 전 분기를 덮는다. UI 는
  판단하지 않고 `logo_asset()` 결과를 그리기만 한다 — ADR-0009 §2 와 같은 구조.

### 정직한 인정 — 이건 라이선스 없는 재호스팅이다

13개 **식별 가능한 소규모 한국 판매자**의 브랜드 자산을 허락 없이 우리 저장소에 복제한다.
지명적 사용이라는 논거는 방향은 맞지만 면허가 아니고, Meta 플랫폼 약관과도 별개 문제다.
감수한 근거는 세 가지다: 저해상 1개, 항상 링크백, 파일 삭제로 즉시 철회(§3). 이 셋 중
하나라도 무너지면 이 결정의 근거도 같이 무너진다.

## 대안

- **모노그램 전용**: 정책 리스크 0, 비용 0, 절대 안 깨진다. 이미 폴백으로 구현돼 있어 언제든
  후퇴할 수 있다. 기각 이유는 하나 — 실제 로고가 주는 브랜드 인지를 얻지 못한다.
- **핫링크(참조 유지)**: §1 을 안 건드려도 되지만 **동작하지 않는다**. 서명 만료 + referrer
  차단으로 수일 내 전량 깨진다. 이건 선택지가 아니라 착시다.
- **판매자 사전 동의 게이트**: 가장 방어 가능한 자리다. 동의한 핸들만 로고, 나머지는 모노그램.
  기각이 아니라 **보류** — 아웃리치가 데모를 블로킹하기 때문이고, §3 의 철회 경로가 이미
  사후 대응을 싸게 만든다. 배포 후 문의가 오면 이 안으로 승격한다.
